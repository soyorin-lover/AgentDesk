### 实测中发现并修复的缺陷

每一条都是先在浏览器里观察到症状，再定位到代码：

1. **创建任务后主区不切换** —— 列表更新了，但主区仍显示「还没有任务」。`create` 意图没有把新任务设为当前。
2. **侧栏状态不随之刷新** —— 事件到达后只重读了当前任务详情，任务列表停在 `处理中`，而主区已是 `待审查`。
3. **失效事实只在增量订阅里捕获** —— `restart()` 后的全量补读路径不重新推导它，导致**重读一次就丢失**，界面退回含糊的「未接受」。已把推导提取为 `deriveInvalidated()`，补读与增量共用。
4. **版本冲突的重试语义错误** —— 冲突时把旧请求留在「待重试」，但旧 `expectedVersion` 原样重发必然再次冲突，等于把用户卡死。已改为：业务错误清空待重试（重试只对**网络结果不明**有意义），重新读取后由用户重新发起（那时取新鲜版本 + 新键）。
5. **`edit` 动作被静默吞掉** —— 后端在工作区 `failed` / `needs_recovery` 时返回 `['edit']`，界面没有对应表单也没有说明。已补一行边界说明（不允许静默丢失一个服务明确列出的动作）。
6. **离开工作台再回来掉回连接表单** —— 令牌本来就在内存里，不该丢。已把连接意图与选中任务提到模块内存（刷新页面仍然重置）。
7. **替身被打进主包** —— 68 kB 源码拖累真实联调路径。已改为动态导入，另成 30.85 kB 分块，主包从 180 kB 降到 149.66 kB。

另有一次是我的**测试探针**错误而非产品缺陷：探针用子串匹配按钮，误点了任务列表里标题含「中止」的条目，一度看起来像中止失效。用精确选择器复测得「已中止」。记录下来以免误判。

## 6. 需要 Codex 配合的接口问题

完整记录见 [`v3-01-接口缺口与确认事项.md`](v3-01-接口缺口与确认事项.md)。要点：

1. **`Acceptance` 没有 `contentDigest`** —— 与「接受绑定三字段」的文档说法不符（`types.ts:9`）。前端因此无法独立校验接受有效性，只能读服务端 `valid`。
2. **`availableActions` 的实际动作名与文档/旧前端契约全不同** —— 实际是 `start` / `feedback` / `snapshot` / `check` / `cancel_check` / `prepare_workspace` / `edit` / `interrupt` / `accept`，且是 `string[]`（无 reason 字段）。前端已按实际值改正。请确认是否冻结。
3. **无接受列表端点** —— 「上次接受已失效」只能从事件流推导，事件被清理就丢失。建议补只读列表端点。
4. **检查 `needs_recovery` 会永久阻塞整个服务** —— `#busy()` 把它计入忙，而 `cancelCheck` 要求 `running`，且没有「确认未知结果」端点。界面因此只能显示「需人工恢复」，用户没有任何可点的恢复动作。请确认运维出口。
5. **`version_conflict` 不返回 `currentVersion`** —— `ApiError` 预留了该字段并会在响应里带上，但 `#version()` 没传。
6. **状态码逐端点说明** —— 文档说「202 仅表示意图」，实际 `POST /tasks` 与 `POST /tasks/:id/snapshots` 是 201，`accept` 是 200。前端按「一律重新查询」处理，不受影响，但文档宜逐端点写明。
7. **项目模式服务的部署约定** —— `port` / `database` / `checkPresets`，以及前端应连接的端口与 `allowedOrigins` 如何配置。本批没有可用服务，真实联调因此未完成。
