# 前端接口需求

给 GPT / Codex 的对接清单。**本批未验证任何执行能力**，以下字段与事件全部来自：

1. 本机 `codex --version` = `0.162.0-alpha.2` 生成的协议 schema，位于 `.agentdesk/protocol/`（39 个 JSON + v1/v2 子目录 + `protocol-ts/` 类型）；
2. 产品文档 [PRODUCT.md](../../AgentDesk/docs/PRODUCT.md) 的状态语义。

**我不猜 App Server 的字段**。凡是标 `待确认` 的地方，是需要 Codex 侧确认或补充的；凡是我从 schema 里读到的，都标了出处。数据库结构不由我决定。

## 1. 前端需要的数据对象

前端只消费下面这些对象。`types.ts` 里与后端形状不一致的部分由 adapter 层转换（见 §5）。

### Task

| 字段 | 类型 | 来源 / 说明 |
|---|---|---|
| `id` | string | 后端生成 |
| `ref` | string | 展示编号，如 `T-142`。**待确认**：后端是否维护独立的人类可读编号 |
| `title` | string | 用户输入 |
| `goal` | string | 用户输入，可为空（草稿） |
| `acceptance` | `{id, text, met}[]` | 用户输入；`met: boolean \| null`，null = 未判定 |
| `status` | TaskStatus | 8 值枚举，见 §2 |
| `latestRunStatus` | RunStatus \| null | 冗余字段，由后端算好返回可省前端一次遍历 |
| `block` | BlockReason \| null | 见 §3。**与 status 正交**，可同时存在 |
| `runs` | Run[] | 最多返回最近 N 次；前端只渲染全部 |
| `changes` | ChangeSet \| null | 见下 |
| `integration` | Integration | 见下 |
| `workspace` | Workspace | 见下 |
| `createdAtMs` / `updatedAtMs` | number | 毫秒时间戳 |

### Run

| 字段 | 说明 |
|---|---|
| `id` | 后端生成，一次「运行」= App Server 的一个 turn |
| `threadId` / `turnId` | 对应协议里的 `threadId` / `turn.id` |
| `index` | 第几次运行，从 1 开始，前端用于显示「第 N 次运行」 |
| `status` | RunStatus，7 值枚举 |
| `startedAtMs` / `finishedAtMs` | `finishedAtMs` 为 null 表示未结束 |
| `model` | 原文展示，**不由前端推断**。协议中模型相关字段在 `ClientRequest.json` 有 `model` 与 `modelProvider` |
| `baseCommit` | 本轮起点提交，前端展示为 `base 3c1d7ae` |
| `events` | TimelineEvent[]，见 §4 |
| `outcome` | RunOutcome \| null，本轮结论摘要 |

### RunOutcome

| 字段 | 说明 |
|---|---|
| `summary` | 一句话结论 |
| `changedFiles` / `additions` / `deletions` | 变更统计 |
| `checks` | Check[]，**必须包含未运行项**，见 §2 |
| `error` | 失败原因，可选 |
| `nextSteps` | 后端可给建议；前端也可自行推导（当前是前端推导的） |

### Check

| 字段 | 说明 |
|---|---|
| `id` / `name` | 检查标识与显示名 |
| `command` | **真实执行的命令原文**，未运行为 null |
| `status` | `notRun \| running \| passed \| failed \| error` |
| `exitCode` | number \| null。**0 是有效值**，不能用 falsy 判断 |
| `durationMs` | number \| null |
| `output` / `stderr` | 原始输出 |
| `runId` | 由哪次运行产生；集成后的检查为 null |

> **硬要求**：检查项必须显式返回 `status: 'notRun'`，不能省略。前端要据此渲染「未运行」标签。省略会让界面把「没跑」显示成什么都没发生，用户会默认它通过了。

### DiffFile / DiffHunk / DiffLine

前端消费**结构化 diff**，不接收裸文本 patch：

```
DiffFile { path, oldPath?, kind: 'add'|'modify'|'delete'|'rename',
           additions, deletions, hunks: DiffHunk[], binary? }
DiffHunk { header: string,            // "@@ -14,17 +14,30 @@"
           lines: DiffLine[] }
DiffLine { kind: 'ctx'|'add'|'del', oldNo: number|null, newNo: number|null, text: string }
```

**理由**：界面要把增删行分色渲染、要显示双列行号、要在大量文件时折叠。裸 patch 需要前端重新解析，容易解析错。若后端只方便给 patch，请在 adapter 层转成上述结构（`git diff --numstat` + 逐行解析）。

### ChangeSet

| 字段 | 说明 |
|---|---|
| `baseRef` | 变更基线的提交或分支 |
| `worktreePath` / `branch` | 隔离工作区的路径与分支 |
| `files` | DiffFile[] |
| `uncommitted` | 未提交改动数，前端用于在集成前提示 |

### Workspace

| 字段 | 说明 |
|---|---|
| `repoPath` / `worktreePath` / `branch` / `baseBranch` | 路径与分支 |
| `env { os, node, git, codexVersion, connection }` | 环境探测结果 |
| `connection` | `connected \| connecting \| disconnected`，前端据此显示彩点 |

### Integration

| 字段 | 说明 |
|---|---|
| `targetBranch` | 集成目标 |
| `status` | `idle \| running \| succeeded \| conflict \| checkFailed` |
| `mergedCommit` | 成功时的合并提交；冲突时为 **null**（无部分合并） |
| `conflictFiles` | 冲突文件列表 |
| `checks` | 集成后的检查，与运行检查**分开** |
| `startedAtMs` / `finishedAtMs` / `message` | 时间与结果说明 |

## 2. 状态枚举（前后端必须一致）

### TaskStatus（8 值，与 PRODUCT.md 一致）

`draft` `ready` `inProgress` `inReview` `accepted` `integrated` `verified` `cancelled`

### RunStatus（7 值，与 PRODUCT.md 一致）

`queued` `running` `waitingUser` `succeeded` `failed` `interrupted` `resumable`

### CheckStatus（5 值）

`notRun` `running` `passed` `failed` `error`

- `error` 与 `failed` 区分：`error` 是命令没跑起来（环境/依赖问题），`failed` 是跑了但非零退出。前端文案不同（"无法执行" vs "失败"）。

### 状态推进规则（后端应保证，前端也会防御）

| 事件 | 允许的迁移 |
|---|---|
| 运行成功 | `inProgress` → `inReview`（**不是** `verified`） |
| 接受结果 | `inReview` → `accepted`（**不触发**集成） |
| 集成成功 | `accepted` → `integrated` |
| 集成后检查失败 | `accepted` → `integrated` **且**带 `checkFailed` 阻塞 |
| 最终验收 | `integrated` → `verified`（需单独动作） |

## 3. 阻塞原因（BlockReason）

**与 TaskStatus 正交**，可同时存在：一个 `inProgress` 任务可能因等待审批而阻塞。

```ts
BlockReason {
  kind: 'question' | 'approval' | 'processExited' | 'connection'
      | 'mergeConflict' | 'checkFailed';
  summary: string;      // 一句话，直接展示
  runId?: string;
}
```

前端用法：任务头部用独立 banner 显示，与状态芯片**分开**。右栏队列按 `kind` 决定紧急度排序。

**请后端不要**把阻塞编码进 `status` 里（例如加一个 `blocked` 状态）。产品文档明确要求两者是分开记录的。

## 4. 前端需要的事件流

以下方法名与字段**直接取自本机 schema**，可据 `ServerNotification.json` / `ServerRequest.json` 交叉核对。

### 4.1 服务端通知 → 时间线事件

| 协议方法 | 前端事件 | 用到的字段 |
|---|---|---|
| `turn/started` | 轮次开始 | `threadId`, `turn.id`, `turn.items` |
| `turn/completed` | 轮次结束 | `turn.status`, `turn.durationMs`, `turn.error` |
| `item/started` | 项开始 | `item`, `threadId`, `turnId`, `startedAtMs` |
| `item/completed` | 项完成 | `item`, `completedAtMs` |
| `item/agentMessage/delta` | 消息流式 | `delta`, `itemId`, `turnId` |
| `item/reasoning/summaryTextDelta` | 思考摘要流式 | `delta` |
| `item/commandExecution/outputDelta` | 命令输出流式 | `delta`, `itemId` |
| `item/fileChange/outputDelta` | 文件变更输出 | `delta` |
| `item/fileChange/patchUpdated` | 变更内容更新 | `itemId` |
| `error` | 错误事件 | `error`（TurnError）, `willRetry` |
| `warning` | 警告 | `message`, `threadId` |
| `thread/status/changed` | 会话状态变化 | `status.type` ∈ `notLoaded\|idle\|systemError\|active`, `status.activeFlags` ∈ `waitingOnApproval\|waitingOnUserInput` |
| `thread/tokenUsage/updated` | Token 使用 | 前端本批未展示，可供后续使用 |

### 4.2 ThreadItem 类型 → 时间线事件（取自 `ThreadItem` 定义）

`ThreadItem` 是 tagged union，前端按 `item.type` 分派：

| `item.type` | 前端渲染 | 关键字段 |
|---|---|---|
| `userMessage` | 你的指令 | `id`, `content`, `clientId` |
| `agentMessage` | Codex 消息 | `text`, `phase`(=`commentary`\|`final_answer`), `delivery` |
| `reasoning` | 思考摘要（折叠） | `summary`, `content` |
| `commandExecution` | 命令卡片 | `command`, `cwd`, `exitCode`, `durationMs`, `status`, `aggregatedOutput` |
| `fileChange` | 文件变更卡片 | `changes`, `status` |
| `plan` | 计划 | `text` |
| `mcpToolCall` | 工具调用 | `server`, `tool`, `arguments`, `status` |
| `dynamicToolCall` | 动态工具 | `tool`, `arguments`, `success` |
| `webSearch` | 搜索 | `query`, `results`, `action` |
| `enteredReviewMode` / `exitedReviewMode` | 审查模式标记 | `review` |
| `contextCompaction` | 上下文压缩标记 | `id` |

> 前端当前只渲染前 7 类 + 折叠显示其余的通用形态。若后端要新增类型，请一并给出 `type` 字面量。

### 4.3 服务端请求 → 需要用户响应（`ServerRequest.json`）

这些是**反向请求**（服务端问前端），前端必须回响应。

#### 提问

| | |
|---|---|
| 方法 | `item/tool/requestUserInput`（另有 `ToolRequestUserInputParams` 独立定义） |
| 请求字段 | `threadId`, `turnId`, `itemId`, `isBlocking`, `questions[]` |
| `questions[]` | `{ id, header, question, options[] \| null, isOther, isSecret }` |
| `options[]` | `{ label, description }` |
| 响应字段 | `{ answers: { [questionId]: { answers: string[] } } }` — 取自 `ToolRequestUserInputResponse.json` |

前端行为：渲染为黄色左边框卡片 + 选项列表 + 自由输入框（`isOther` 为 true 时）。回答后作为响应回传。

> **注意**：schema 中 `autoResolutionMs` 已标注 `@deprecated`（提示改用 `isBlocking`）。前端用 `isBlocking` 判断是否阻塞本轮。

#### 审批

| 方法 | 前端分类 | 决策值域（取自 schema） |
|---|---|---|
| `item/commandExecution/requestApproval` | `commandExecution` | `accept` \| `acceptForSession` \| `acceptWithExecpolicyAmendment` \| `applyNetworkPolicyAmendment` \| `decline` \| `cancel` |
| `item/fileChange/requestApproval` | `fileChange` | `accept` \| `acceptForSession` \| `decline` \| `cancel` |
| `item/permissions/requestApproval` | `permissions` | 见 `PermissionsRequestApprovalResponse.json` |
| `mcpServer/elicitation/request` | MCP 主动询问 | 见对应 schema |

**响应字段**：

```ts
// CommandExecutionRequestApprovalResponse
{ decision: 'accept' | 'acceptForSession' | {...} | 'decline' | 'cancel' }

// FileChangeRequestApprovalResponse
{ decision: 'accept' | 'acceptForSession' | 'decline' | 'cancel' }
```

**语义**（取自 schema 内 description）：

| 决策 | 含义 |
|---|---|
| `accept` | 批准本次 |
| `acceptForSession` | 批准，且**本次会话内同类操作不再询问** |
| `decline` | 拒绝，**本轮继续**（模型会换做法） |
| `cancel` | 拒绝，**并立即中止本轮** |

前端行为：
- 四个按钮分别对应这四个决策，措辞直译语义（"仅批准本次" / "批准，本次会话内不再询问" / "拒绝，本轮继续" / "拒绝并中止本轮"）。
- `acceptForSession` 的授权范围更大，界面上**用文字说明代价**，不只放在 tooltip 里。当前文案来自 `event.sessionScopeHint`。
- `acceptWithExecpolicyAmendment` 与 `applyNetworkPolicyAmendment` 本批**未在界面暴露**——它们会写入持久的策略规则，属于"会话级之上的授权"，需要产品决策后再加。**待确认**：这两个决策是否应出现在首版界面？

请求字段（`CommandExecutionRequestApprovalParams`）：`itemId`, `threadId`, `turnId`, `startedAtMs`（`FileChangeRequestApprovalParams` 另有 `reason`, `grantRoot`）。

`FileChangeRequestApprovalParams.reason` 前端已用于展示"模型给出的理由"。
`grantRoot` 标注为 `[UNSTABLE]`（"是否生效尚不明确"），前端本批未使用。

## 5. 操作清单

前端会发出的操作。**这些是前端需要的接口，不是协议方法名**——内部用什么方法请后端决定。

| 操作 | 语义 | 前端约束 |
|---|---|---|
| 创建任务 | 落库，可能同时启动运行 | 无目标/验收条件时只能存草稿 |
| 启动运行 | 新建 thread + turn | 需先建 worktree |
| 回答提问 | 响应服务端请求 | — |
| 处理审批 | 响应服务端请求 | 必须能表达四种决策 |
| 补充指令 | **同一 turn 内**继续 | 不得新建 Run |
| 中止运行 | 中止当前 turn | **不得回滚已产生的改动** |
| 恢复会话 | 沿用上下文继续 | 与重跑不同；**不恢复已结束的进程** |
| 重新执行 | 丢弃上下文，新建 Run | 与恢复不同 |
| 接受结果 | 状态 → `accepted` | **不得触发集成** |
| 执行集成 | 合并到目标分支 | 独立操作；三种结局 |
| 最终验收 | 状态 → `verified` | 需在所有检查有结论后 |

> **待确认（重要）**：以上「中止」「恢复」「补充指令」三者在 0.162.0-alpha.2 上的**实际可用性尚未验证**（ENVIRONMENT.md 只验证了初始化握手）。当前界面把它们标为设计假设。请 Codex 批次给出实测结论后，我再据结果调整界面（可能某些操作需要降级为"暂不支持"）。

## 6. 错误反馈需求

前端需要能区分以下几类，因为用户要采取的行动不同：

| 类别 | 用户该做什么 | 前端呈现 |
|---|---|---|
| 运行失败（`turn.status = failed`） | 看保留结果，决定恢复/重跑/补指令 | 红色横幅 + 折叠的错误详情 + 后续操作区 |
| 命令非零退出 | 看输出 | 命令卡片标红，退出码显眼 |
| 检查无法执行（`error`） | 修环境/依赖 | 与"失败"文案区分 |
| 连接断开 | 等待或重连 | 左栏红点；不谎称任务已取消 |
| 合并冲突 | 决定如何解决 | 冲突文件列表 + "没有部分合并"说明 |
| 集成后检查失败 | 追加修复提交 | 说明"变更已在目标分支上" |
| 服务端错误但会重试 | 等待 | `willRetry = true` → "本轮出错，服务端将重试" |

**不要**把错误统一成一句"操作失败"。用户在失败时最需要知道的是**下一步该点哪里**。

## 7. 时间戳约定

- 全部用**毫秒 Unix 时间戳**（`number`）。协议里 `Turn.completedAt` 是**秒**、`ItemStartedNotification.startedAtMs` 是**毫秒**，adapter 层需统一为毫秒。
- 前端不做时区转换，直接用 `Date` 本地化显示。
- 相对时间（"4 分钟前"）由前端计算，需要后端给绝对时间戳——不要给预格式化的字符串。

## 8. 分页与规模

| 数据 | 本批处理 | 后续建议 |
|---|---|---|
| 任务列表 | 全量返回（演示 8 条） | 分页，按 `updatedAtMs` 倒序 |
| 运行历史 | 全量返回 | 列表只给最近 N 次，详情按需拉 |
| 事件时间线 | 全量返回 | **必须支持分页**。长会话事件可达数万条 |
| 变更文件 | 全量 | 大型重构可能上千文件；建议给 numstat 概览 + 按需拉单个文件的 hunks |
| 命令输出 | 全量 | 建议后端截断并标注（前端已做 40 行折叠，但传输层也该限制） |

## 9. 待确认事项汇总

1. **`ref`（`T-142` 这类编号）** 由谁生成？后端是否维护？还是用短哈希？
2. **结构化 diff** 后端能否直接提供？若只能给 patch，需要确认由哪一侧解析。
3. **`acceptWithExecpolicyAmendment` / `applyNetworkPolicyAmendment`** 是否需在首版界面暴露？会写持久策略，风险高于会话级授权。
4. **中止 / 恢复 / 补充指令的实际可用性**——需 Codex 实测结论（见 CODEX-BATCH-01.md 验证顺序第 5、6 条）。
5. **并行工作区隔离**：`Workspace` 对象按任务返回，还是需要一个跨任务的环境视图？前端当前假设按任务返回。
6. **Token 用量**（`thread/tokenUsage/updated`）是否要在界面展示？本批未做。若要展示，需明确产品口径——**不要展示"节省了多少"这类未经证实的指标**。
7. **事件时间线的分页游标**形式。
