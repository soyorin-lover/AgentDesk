# v2 接口对齐说明

日期：2026-10-08 · 依据 `AgentDesk/src/backend/types.ts`、`docs/BACKEND-USAGE.md`、`docs/BACKEND-API-DRAFT.md`

本文件说明前端如何与第 2 批 A 后端对齐，以及**当前还不能做**什么。

---

## 1. 演示数据与真实数据

### 分离方式

```
src/v2/data.ts              原始素材（构造内容，不来自执行）
        ↓  backend/demo.ts   适配层：转成 backend/types.ts 的形状
backend/types.ts            契约：逐字段对齐主项目 src/backend/types.ts
        ↓
组件                         只消费契约类型
```

组件层不直接导入 `data.ts` 的任何**任务**。适配层负责三件事：字段改名（`inProgress` → `in_progress`、`agentId` → `agentInstanceId`）、补后端字段（`schemaVersion`、`version`、`phase`）、生成快照与摘要。

### 界面上如何区分

| 位置 | 演示模式 | 真实模式（接线后） |
|---|---|---|
| 侧栏左下角 | 橙色 `演示` 标签 + 「演示数据 · 未连接后端」 | 常规标签 + 「后端 · <endpoint>」 |
| 接受确认框 | 底部一段说明：真实模式会带 `expectedVersion` 与 `snapshotId` | 同一段落改为陈述实际行为 |
| 发送后提示 | 「演示：未发送到真实引擎」+ 真实端点名 | 显示 `Idempotency-Key` 与提交结果 |

`capability.tsx` 的 `DataSource.mode` 是唯一开关；`LIVE_AVAILABLE` 目前为 `false`。

### 检查状态：结构上不可能假装通过

后端 `Changes.checks` 的类型是单字面量 `'not_run'`，不是三态枚举：

```ts
export type ChecksState = 'not_run';   // 不是 'passed' | 'failed' | 'not_run'
```

因此真实模式**无法**表达「检查通过」。前端另提供 `liveChecks()`，真实模式下只能产出一项 `not_run`，并写明原因。演示模式里那些「类型检查 通过」的示例检查全部带 `demo: true`，接线时必须整体丢弃。

界面上的措辞也已经对齐：审查页底部决策条写「**检查未运行** · 后端本批不执行检查；这里展示不了通过或失败」，不再出现 v2 早期写死的「2 项通过」。（评审指出的 `AppV2.tsx:189` 固定值已移除。）

## 2. 接受与检查的版本关联

### 不能只绑提交号

评审指出：模型改动通常**尚未提交**，同一个 `HEAD` 下工作区内容可以多次变化。所以版本身份是三个字段：

```ts
export interface SnapshotIdentity {
  runId: string;
  snapshotId: string;
  contentDigest: string;
}
```

`Acceptance` 记录带 `taskId / runId / snapshotId / contentDigest`。提交号（`baseHead` / `head`）只作为附加上下文展示，不参与相等判断。

### 失效判定

`acceptanceValidity(acceptance, current)` 逐字段比较，四种失效原因分别显示：

| 原因 | 触发 |
|---|---|
| `new_run` | 之后产生了新的运行 |
| `snapshot_refreshed` | 显式刷新快照后摘要变化 |
| `external_change` | 检测到工作区被外部修改 |
| `no_snapshot` | 还没有可接受的快照 |

失效后**保留记录**并标记原因，界面显示「上次接受已失效：<原因>」，而不是退回「未接受」——用户需要知道曾经接受过、以及为什么不算数了。

### 按任务隔离

应用级布尔值已删除。接受记录存在 `acceptances: Acceptance[]` 里，按 `taskId` 查找。任务列表、概览、上下文栏、审查决策条都调用同一个 `validAcceptanceOf(taskId)`。

种子状态也遵守这条不变式：演示数据里声明为 `accepted` 的任务，必须由一条绑定其快照的记录支撑；没有快照的会退回 `in_review`（实测 t139 即为此情况）。

### 已接受任务仍可反馈

实测发现并修复：接受后「要求修改」按钮会消失。但后端草案明确允许「对待审查/已接受任务反馈修改 → 新建运行 → 旧接受失效」。现在两种状态都保留该入口。

## 3. 按 availableActions 展示操作

后端在读取 Task 时返回 `availableActions`。前端结构：

```ts
export interface ActionAvailability { allowed: boolean; reason?: ErrorCode }
export interface AvailableActions {
  startRun: ActionAvailability;
  requestChanges: ActionAvailability;
  interrupt: ActionAvailability;
  refreshSnapshot: ActionAvailability;
  accept: ActionAvailability;
}
```

**未列出的动作一律视为不可用。** 界面只渲染 `allowed` 的动作。

### 本批明确不支持的能力

`UNSUPPORTED_ACTIONS` 列出并在界面上标注，**不给可点按钮**：

| 能力 | 界面处理 |
|---|---|
| 审批 / 提问 | 卡片保留（说明动作与影响范围），底部写「允许 / 拒绝在本批不可用」 |
| 运行中补充指令 | 输入框 `disabled`，提示「执行中不能提交新指令（本批无运行中补充能力）」 |
| 恢复会话 | 失败卡片写「需要人工恢复，本批没有恢复接口」 |
| 更换实例 | 写「更换实例不可用」（草案：本批禁止执行后切换实例） |
| 集成 / 最终验收 | 侧栏无入口；接受后只显示「未集成」 |
| 执行检查 | 检查面板固定 `not_run` |

`needs_recovery` 的任务禁止后续启动与接受（草案规则），界面同时禁用「接受结果」并给出原因。

### 待确认

`availableActions` 的**字段名**是我按后端能力推导的。`BACKEND-USAGE.md` 只说明响应含该字段，未给清单。需要 Codex 确认字段名与取值；在此之前前端按「未列出即不可用」的保守规则处理，不会误放行。

## 4. 下一批最小联调方案

单专用仓库、`codex-local`、单任务顺序运行。**仅方案，本轮未改后端、未接线。**

### 前置：连接入口

令牌不写进源码或 URL（`BACKEND-USAGE.md` 明确要求）。方案：

1. 新增本机连接设置页（不放在主导航，从侧栏底部设置进入）。
2. 字段：服务地址（默认 `http://127.0.0.1:4317`）、访问令牌、连接测试。
3. 令牌只存浏览器 `localStorage`，不进 `data.ts`、不进 URL、不进日志。
4. 所有请求带 `Authorization: Bearer <token>`；SSE 用**可带鉴权头的 fetch 流**，不用 `EventSource`。
5. 服务端 `allowedOrigins` 需显式加入前端开发来源（当前为 `http://localhost:5311`；正式接入时确定固定端口）。

### 切片顺序

| # | 步骤 | 端点 | 前端要点 |
|---|---|---|---|
| 1 | 读取绑定与能力 | `GET /bootstrap` | 用返回的实例与能力**替换**演示能力表；未接入引擎保持不可选 |
| 2 | 创建任务 | `POST /tasks` | `Idempotency-Key`；目标或验收条件不完整则为 draft，界面按返回状态显示 |
| 3 | 启动运行 | `POST /tasks/:id/runs` | 只提交 `{expectedVersion}`；**202 只表示意图已记录**，界面显示「已请求，等待后端确认」，不显示为运行中 |
| 4 | 执行与事件 | `GET /tasks/:id` + `events?after=` + `events/stream` | 按 `seq` 去重补读；`lastEventSeq` 与快照同事务取得，初始化缝隙不能漏事件；未知事件类型忽略但**不改任务状态** |
| 5 | 中止或结束 | `POST /runs/:id/interrupt` | 202 后显示「请求已记录」；只有收到真实 `aborted` 才显示已中止。已完成运行保留真实结果，不伪造中止 |
| 6 | 快照审查 | `POST /tasks/:id/snapshots` + `GET /tasks/:id/changes` | 无活动运行时才允许；`ReviewFile.diff` 走已实现的统一 diff 解析器；`kind != text` 显示为不可接受 |
| 7 | 接受 | `POST /tasks/:id/accept` | 带 `{expectedVersion, snapshotId}`；`snapshot_stale` 映射为「改动已变化，接受失效」 |
| 8 | 反馈修改 | `POST /tasks/:id/runs` + `input` | 产生新运行；**旧接受失效**；沿用同引擎会话续接上下文 |

### 前端已就绪的部分

- 统一 diff 解析器（后端给的是 diff **文本**，不是结构化 hunk）—— 已按真实形状实现
- 状态映射（`TaskStatus` / `RunStatus` / `phase` 已对齐）
- 接受身份三字段与失效原因
- 能力门禁与不可用说明
- 事件 `seq` 去重所需的数据结构（`EventEnvelope`）

### 需要后端确认/补充

1. `availableActions` 字段清单与取值。
2. 事件 `type` 的完整联合（当前草案给了 11 个；`EventType` 用 `string & {}` 开放，但界面需要知道哪些会影响状态）。
3. `GET /tasks/:id` 响应中 `snapshot` 是摘要还是完整对象（影响是否要额外请求文件 diff）。
4. 401 的处理约定：令牌失效时是否返回可区分的 `code`，界面据此引导到连接设置。
5. 快照刷新是否自动发生（草案说只在显式刷新与接受前校验时检查磁盘）。

### 明确不在本批联调范围

审批、提问、运行中补充指令、恢复、换实例、检查执行、集成、最终验收、自动 worktree、多引擎。不从第一批协议证据推断这些已支持。

## 5. 本轮发现的判断修正

评审基于源码，未做浏览器实测。实测后有一处需要更正，附证据：

**评审第 3 条关于「文件栏不会普遍自动收起」**：判断成立，本轮已按此实现自动降级（见验收记录 §4 的宽度扫描）。但评审未提到的两点在实测中暴露，已修复：

1. **演示 diff 文本不是合法统一 diff**。原生成器写的是 `@@ <函数签名>` 而非 `@@ -旧起,旧数 +新起,新数 @@`，导致并排视图解析出 0 个 hunk（`splitPanes: 2` 但无行）。这会让「并排截断」的问题被掩盖成「并排空白」。已改为生成标准 hunk 头。
2. **代码单元格曾设 `overflow: hidden` + `text-overflow: ellipsis`**。评审第 4 条指出；实测确认 `textOverflow` 现为 `clip`，`overflow` 为 `visible`，长行通过父容器横向滚动完整可读（实测 1934px 内容 / 931px 视口）。
