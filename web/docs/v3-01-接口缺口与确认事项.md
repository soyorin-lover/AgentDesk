## 1. 文档与源码不一致（需要确认哪一边是权威）

### 1.1 `Acceptance` 没有 `contentDigest`

- `docs/BACKEND-BATCH-03-API.md` 与前端契约都写「接受绑定三字段 `runId` + `snapshotId` + `contentDigest`」。
- `src/backend/types.ts:9` 实际是：
  ```ts
  type Acceptance = { schemaVersion: 1; id; taskId; runId; snapshotId; acceptedAt: string; valid: boolean };
  ```
  **没有 `contentDigest`，也没有返回摘要字段。**
- 影响：前端**无法自行校验接受是否仍然有效**，只能读服务端的 `valid` 与任务上的 `acceptedSnapshotId`。
  摘要相等的判断目前完全在服务端（`service.ts` 的 `accept()` 里用 `captureChanges` 比对）。
- 请确认：是接受记录**应**带 `contentDigest`（则补字段），还是前端**不应**再把它当作可读字段（则改文档）。

### 1.2 `availableActions` 的实际取值与文档/前端契约都不同

- 实际取值（`service.ts:222`）：`start`、`feedback`、`snapshot`、`check`、`cancel_check`、`prepare_workspace`、`edit`、`interrupt`、`accept`。
- 前端旧契约文件里写的是 `startRun` / `requestChanges` / `refreshSnapshot` / `accept` —— **名字全错**，已在本批按实际值改正。
- 另外它是 `string[]`，**不是** `{allowed, reason}[]`。没有 reason 字段，界面只能自己给原因文案。
- 请确认：这套动作名是否冻结？后续新增 `integrate` / `verify` / `resume` 时如何保持兼容。

### 1.3 `availableActions` 里出现了前端未实现的 `edit`

- `service.ts:222` 在「工作区未就绪且尚无运行」或「任务 `draft`」时会列出 `edit`。
- 本批前端只做了创建与切换，**没有做任务编辑表单**。界面因此会出现一个「未实现的可用动作」。
- 请确认：`edit` 是否属于本批范围；若有编辑需求，前端下一批补 `PATCH /tasks/:id` 表单。

## 2. 状态码语义比「202 一律是意图」更细

文档说「202 仅表示持久化意图」。实际（`http.ts:82-96`）：

| 端点 | 实际状态码 |
|---|---|
| `POST /tasks` | **201** |
| `POST /tasks/:id/runs` | 202 |
| `POST /tasks/:id/workspace` | 202 |
| `POST /tasks/:id/checks` | 202 |
| `POST /checks/:id/cancel` | 202 |
| `POST /runs/:id/interrupt` | 202 |
| `POST /tasks/:id/snapshots` | **201** |
| `POST /tasks/:id/accept` | **200** |

前端已按「一律重新查询，不拿返回值当终态」处理，所以不影响本批；
但文档若要让第三方照着写客户端，建议逐端点写明。

## 3. 前端无法表达、但产品上真实存在的状态

### 3.1 「上次接受已失效」没有查询接口

- 失效动作在 `service.ts:266` 记为事件 `task.acceptance_invalidated`，含 `reason`。
- **没有** `GET /tasks/:id/acceptances` 之类的列表端点，`Acceptance` 也没有单独的读取路由。
- 因此前端显示「上次接受已失效：<原因>」**只能靠事件流里的历史事件**推导。
  事件补读是从 `after=0` 全量拉取，所以可行；但若事件被清理或客户端从中间接入，就丢了。
- 请确认：是否补一个只读的接受列表端点（`{items: Acceptance[]}`）。这不改变状态语义，只是让事实可查询。

### 3.2 `needs_recovery` 的检查会永久阻塞该服务

- `service.ts:96` 的 `#busy()` 把 `status === 'needs_recovery'` 的检查也计为忙。
- 检查进入 `needs_recovery` 后，**该服务上所有任务的 `start` / `snapshot` / `accept` 都被拒**（409 `active_run`）。
- 而 `cancelCheck` 要求 `status === 'running'`（`service.ts:150`），**无法对 `needs_recovery` 的检查取消**。
- 也没有「清理/确认未知结果」的端点（交接文档说明这是故意的，但没有出口）。
- 影响：一旦出现检查 `needs_recovery`，界面只能显示「需人工处理」，用户在当前服务上**没有任何可点的恢复动作**。
- 请确认：这是预期的运维出口（改数据库/重启并人工诊断），还是需要补一个显式的「确认未知结果」端点。

### 3.3 `interrupt` 在 `starting` 阶段不可用

- `service.ts:365` 要求 `run.phase === 'executing' && this.#executions.has(id)`。
- 也就是说运行刚创建、还在 `starting` 时，`availableActions` 不含 `interrupt`，界面没有中止按钮。
- 这是合理的（执行器还没就绪），只是提示：**短运行可能整个生命周期都看不到中止按钮**。
  前端已按此实现，不视为缺陷，仅记录以免被误判为「界面漏了按钮」。

## 4. 版本冲突不带 `currentVersion`

- `errors.ts` 的 `ApiError` 支持可选 `currentVersion`，`http.ts:102` 也会在响应里带上它。
- 但 `service.ts:240` 的 `#version()` 抛的是 `new ApiError(409, 'version_conflict')`，**没有传 currentVersion**。
- 实际响应因此是 `{"error":{"code":"version_conflict","message":"version_conflict","retryable":false}}`。
- 前端已按文档要求「重新读取详情再呈现冲突」处理，不需要这个字段也能工作；
  但字段既然预留了，请确认是否要填上，否则建议从 `ApiError` 里删掉以免误导客户端作者。

| 行为 | 源码依据 | 前端处理 |

| 只有 `passed` + `current` 可以说「当前版本检查通过」 | `service.ts:106` + API 文档 | 见 `src/v2/live/presentation.ts` 的 `presentCheck()`，有 15 条测试覆盖 |
