# AgentDesk 前端设计说明（第 1 批）

面向本批「核心流程设计 + 可点击原型」的交付说明。技术实现见 [README.md](../README.md)。

---

## 1. 用户与目标

**使用者**：一个人。他是独立开发者，同时在推进多个改动，靠 Agent 干活。

**他来这个界面的理由**：不是"看 Agent 在干什么"，而是**"现在轮到我了"**。多会话并行时，最大的成本不是执行慢，是不知道哪条线上卡着等他。他要的是三秒钟内回答：有哪几件事在等我，分别等什么。

**本批目标**：验证这条判断——把"待处理"做成界面的一等公民，用独立的第三栏承载它，而不是塞进任务列表的状态标签里。

**本批不做**：AI 自动拆解需求、自动排期、多厂商切换、完整 IDE、真实执行接入。

## 2. 信息架构

三栏，一屏不切页。

```
┌──────────────────────────────────────────────────────────────────────────┐
│ 顶栏：品牌 · 项目 · 演示标记 · 未接入执行引擎                              │
├──────────────────────────────────────────────────────────────────────────┤
│ 演示说明条（仅演示模式存在，接入真实执行后移除）                            │
├───────────────┬──────────────────────────────────────┬───────────────────┤
│ 左栏 296px    │ 中栏 flexible                        │ 右栏 344px        │
│               │                                      │                   │
│ 项目 / 仓库   │ 任务头（标题、两条状态、阻塞、        │ 待处理队列         │
│ 环境 / 连接   │        目标、验收条件、工作区）        │                   │
│               │                                      │ 按紧急度排序：     │
│ 创建任务      │ ┌ 执行时间线 │ 变更 │ 检查 ┐          │  1 等待回答        │
│               │                                      │  2 等待审批        │
│ 需要你处理 N  │ 时间线：消息 / 命令 / 文件变更 /      │  3 合并冲突        │
│  ├ T-143 等回答│        提问 / 审批 / 错误，按轮次分段 │  4 检查失败        │
│  ├ T-144 待审查│                                      │  5 执行失败        │
│  ├ T-145 失败  │ 变更：逐行 diff / 文件列表 / 检查证据  │  6 待审查          │
│  ├ T-139 待集成│                                      │  7 待集成          │
│  └ T-146 草稿  │ 检查：按来源分组的检查证据            │  8 草稿待补全      │
│               │                                      │                   │
│ 进行中        │ 后续操作区（失败/中止/待审查时出现）  │ 每个条目写清：     │
│  └ T-142 运行中│                                      │  哪个任务          │
│               │ 演示操作记录                          │  为什么等你        │
│ 已交付        │                                      │  点进去做什么      │
│  └ T-141 已验收│                                      │                   │
└───────────────┴──────────────────────────────────────┴───────────────────┘
```

### 为什么是三栏而不是两栏

最初的设计是两栏（任务列表 + 详情），把待处理做成任务列表里的状态标签。放弃它的原因：**标签只能告诉你"某条任务在等你"，不能告诉你"等什么"**。当等待的是「账户冻结该归为永久失败还是可重试」这种需要具体回答的问题时，标签承载不了。

第三栏的价值在于把"跨任务的待办"聚成一条队列。用户不必在 8 个任务之间逐个点开找哪条卡住了——这一栏本身就是答案。

### 为什么不是仪表盘

没做统计页、燃尽图、Agent 活动热力图。这类图表在本产品里不产生决策。用户需要的是**证据**（命令原文、退出码、逐行 diff），不是趋势。本批只做"决策现场"。

### 左栏分组逻辑

按"用户要做什么"分，不按状态枚举分：

| 分组 | 内容 | 排序依据 |
|---|---|---|
| 需要你处理 | 阻塞 / 待审查 / 草稿 / 待集成 | 按最近更新 |
| 进行中 | 运行中且无需介入 | 按最近更新 |
| 待启动 | 已就绪未运行 | 按最近更新 |
| 已交付 | 已验收 / 已取消 | 按最近更新 |

把「待审查」「待集成」「草稿」放进"需要你处理"而不是各自的独立分组，是因为它们对用户的含义相同：**不推进就停在这里**。

## 3. 核心流程

```
选择已有 Git 仓库
      ↓
创建任务：标题 → 目标 → 验收条件（逐条）
      ↓
   有验收条件？
   ├─ 否 → 草稿（无法启动，界面说明缺什么）
   └─ 是 → 就绪 → 启动运行
              ↓
        建 worktree + 分支 → 排队 → 运行中
              ↓
      ┌── 需要回答？ ──→ 右栏高亮 → 回答 → 继续运行
      ├── 需要审批？ ──→ 右栏高亮 → 批准/拒绝 → 继续或中止
      ├── 失败？ ──────→ 保留结果 → 恢复 / 重跑 / 补充指令
      └── 完成 ────────→ 任务：待审查
              ↓
        查看 diff + 检查证据
              ↓
      ┌── 有意见？ → 补充指令（同一轮内，不新建运行）→ 回到待审查
      └── 接受 ────→ 任务：已接受（代码还没进 main）
              ↓
        独立操作：集成到 main
              ↓
      ┌── 成功 ──────→ 已集成 → 最终验收 → 已验收
      ├── 合并冲突 ──→ 已接受 + 阻塞标记「合并冲突」，无部分合并
      └── 检查失败 ──→ 已集成 + 阻塞标记「检查失败」，需追加修复
```

### 关键设计决定

**1. 「接受结果」和「集成变更」是两个独立步骤，按钮在不同位置。**

接受按钮在"后续操作区"（时间线下方），集成按钮在集成对话框里。中间隔着一个显式打开的对话框，对话框里明确写着"接受结果只是「你认可这次产出」，集成才是把代码放进目标分支"。

理由：把两者合成一个"完成"按钮会让用户在不知情的情况下改掉 main。

**2. 检查未运行必须显式显示，不能留空。**

检查列表的结构是：**没有检查记录 ≠ 全部通过**。没有记录时显示空状态文案"这不是「全部通过」，而是「没有任何证据」"。有记录但某项没跑时，该项显示 `未运行` 标签 + 斜纹底 + "尚未执行，没有可展示的命令与结果"。

理由：`未运行` 被渲染成空白，用户会默认它是通过的。这是本产品最容易出的静默错误。

**3. 恢复会话 ≠ 重新执行，两个按钮并列，各带一句说明。**

| 操作 | 说明文案 |
|---|---|
| 恢复会话 | 沿用这次会话的上下文继续。不会恢复已经结束的系统进程。 |
| 重新执行 | 丢弃这次会话的上下文，从当前基准提交重新跑一遍。与「恢复」不同。 |
| 补充指令后继续 | 把失败原因一并交回模型，要求修正后继续。仍然算同一次运行。 |

**4. 中止不回滚，失败不丢结果。**

中止或失败的任务，其 diff 仍然完整保留在变更视图里。界面上有一句常驻提示："中止不会回滚已经写入工作区的改动。"失败任务额外有一块说明："失败前的文件改动都还在工作区里。"

## 4. 状态语义实现

任务状态与运行状态**是两个维度**，界面必须让它们在任何时刻都分得清。

### 视觉区分手段（多重冗余，不依赖单一通道）

| | 任务状态 | 运行状态 |
|---|---|---|
| 前缀 | 无 | `运行 ·` |
| 圆角 | 全圆角 `999px` | 方角 `3px` |
| 位置 | 左侧 | 右侧 |
| 语义 | 任务走到哪一步 | 最近一次运行的状态 |

即使用户把颜色记混、或在灰度打印下，前缀和圆角仍然能区分两者。

### 阻塞原因单独显示

阻塞不进状态枚举。一个「处理中」的任务可能同时被阻塞——两者都要显示。

任务头部的阻塞信息用一整块 banner 呈现，标题写明"阻塞原因（与上面的状态是两个维度）"，避免读者把它当成第三个状态标签。

### 已编码的不变式

以下规则在状态机层强制（见 `src/state/store.ts`），界面无法绕过：

| 规则 | 实现位置 |
|---|---|
| 执行成功 ≠ 验收通过 | `completeRun` 只把任务推到 `inReview`，不是 `verified` |
| 接受 ≠ 已集成 | `acceptResult` 只推到 `accepted`，不触发集成 |
| 集成完成 ≠ 检查全通过 | `integrate` 的 `checkFailed` 结局：任务为 `integrated` **且**带 `checkFailed` 阻塞 |
| 中止不回滚 | `interrupt` 不改动 `changes.files` |
| 恢复 ≠ 重跑 | 两个独立 action，`resume` 复用 runId，`rerun` 新建 Run |
| 补充指令不新建运行 | `requestChanges` 往同一个 Run 里追加事件 |
| 关闭页面不取消任务 | 演示模式重载即回到种子态；真实接入后此状态由服务端持有 |

## 5. 空状态 / 加载 / 错误 / 断连

| 场景 | 处理 |
|---|---|
| 无任务 | 左栏空 + 右栏"没有待处理事项" |
| 无运行记录 | 时间线空状态，给出启动按钮（草稿时禁用并说明原因） |
| 无验收条件 | 任务头显示警告条 + 说明"草稿状态无法启动运行" |
| 无检查记录 | 空状态明确说明这不是"全部通过"，而是"没有任何证据" |
| 无变更 | 空状态区分两种情况：本轮没产生改动 / 还没有变更记录 |
| 无待处理 | "所有运行都不需要你介入" |
| 运行中 | 脉冲点 + 顶部 2px 进度条 + "关闭页面不会取消这次运行" |
| 连接状态 | 左栏彩点 + 版本号；断连时显示红点（演示中未触发，样式已就位） |

## 6. 长内容 / 大量数据的处理

| 场景 | 处理方式 |
|---|---|
| 长消息 | 段落保留，代码样式行自动识别为等宽块；最大宽度 82ch |
| 长文件路径 | 中间截断显示尾部 3 段，`title` 给完整路径，附一键复制按钮 |
| 长命令输出 | 超过 40 行只显示尾部 40 行 + "显示前面 N 行"按钮；运行中带渐隐遮罩表示还在增长 |
| 大量变更文件 | 逐行差异默认只展开 2 个文件，其余折叠成"展开其余 N 个文件"；另有文件列表视图可一屏扫完 |
| 长任务列表 | 左栏独立滚动，分组标题 sticky 吸顶 |
| 多轮运行 | 时间线按轮次分段，历史轮次标记"历史运行"，只有最后一轮可交互 |
| 大量待处理项 | 右栏独立滚动，按紧急度排序 |

## 7. 键盘与可访问性

| 操作 | 按键 |
|---|---|
| 创建任务 | `c` |
| 切到时间线 | `1` |
| 切到变更 | `2` |
| 切到检查 | `3` |
| 关闭对话框 | `Esc` |
| 对话框内焦点循环 | `Tab` / `Shift+Tab`（焦点不逃出） |
| 提交验收条件 | `Enter` 在最后一行时新增一行 |

- 所有可交互元素有可见焦点环（`--focus-ring`，两段式，深色背景下高对比）
- 所有状态芯片带 `title` 给出完整含义
- 状态不只用颜色表达（见 §4）
- 图标默认 `aria-hidden`，仅在承载语义时给 `title` 和 `role="img"`
- 模态框有 `role="dialog"` + `aria-modal` + `aria-labelledby`
- 选项卡用 `role="tablist"` + `aria-selected`
- 演示模式标记不只靠颜色，带文字"演示"
- 尊重 `prefers-reduced-motion`：脉冲动效在用户要求减少动效时关闭
