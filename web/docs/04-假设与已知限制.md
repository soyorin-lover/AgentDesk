# 设计假设、待确认事项与已知限制

本批**没有接入真实 Codex 执行**。原型里所有"运行"都是前端脚本推进的演示状态。

---

## 1. 设计假设（界面上标了「设计假设」徽标）

以下能力在界面上**已经做出来了**，但它们的真实可用性**尚未验证**。依据 [ENVIRONMENT.md](../../AgentDesk/docs/ENVIRONMENT.md)：目前在 Windows 上只验证了 Codex App Server 的 `initialize` / `initialized` 握手。

| 假设 | 当前界面表现 | 如果假设不成立，需要怎么改 |
|---|---|---|
| **中止能收到明确的 interrupted 结果** | 中止按钮立即置运行状态为「已中止」，并追加一条 `interrupted` 事件 | 若中止只是断开连接而没有服务端确认，界面必须改成「已请求中止，等待确认」的中间态，不能直接显示「已中止」 |
| **恢复会话 = 沿用上下文继续** | 「恢复会话」按钮在同一 Run 内追加一条 info 事件 | 若恢复实际是新起一次运行，必须拆成两个状态，「第 N 次运行」的计数逻辑要重做 |
| **补充指令可在同一 turn 内送达** | 补充指令追加到同一个 Run 的事件流里 | 若只能新起 turn，界面要改成"新建运行"语义，并说明上下文会延续 |
| **并行工作区彼此隔离** | 每个任务有独立 `Worktree` 对象与分支，右栏可同时显示三条运行中任务 | 若隔离不成立，界面不能承诺"各自只产生预期文件变更"；本批原型里也没展示两个任务同时跑 |
| **审批请求能到达前端** | 审批卡片 + 四种决策按钮 | 若首版无法触发审批，整个审批卡片需要降级为"只读记录"或移除 |
| **`isBlocking` 可判定是否阻塞** | 用它决定是否把任务标为「等待用户」 | 若协议实际不给这个语义，需要从其他字段推断 |
| **变更文件能拿到结构化 diff** | 逐行 diff 视图、双列行号、增删分色 | 若只能给裸 patch，adapter 层需要加解析器；解析失败要有降级（显示 patch 原文） |
| **关闭页面不取消任务** | 演示模式下重载回到种子态，界面文案承诺"关闭页面不会取消这次运行" | 这条依赖服务端持有状态。真实接入前，界面这句承诺**只是设计意图** |

**这些标签在界面上是可见的**（`Assumption` 组件，悬停给出完整说明），不是藏在文档里。用户看到的界面不应该比实际能力更自信。

## 2. 已知限制

### 本批范围内的取舍

| 限制 | 原因 |
|---|---|
| 无移动端布局 | 提示词明确移动端不是本批重点；按桌面 1600×900 优化 |
| 不支持新建/克隆 Git 仓库 | 核心流程是"选择已有仓库"，创建对话框只收路径 |
| 不支持在浏览器内编辑仓库文件 | 首版不做完整 IDE |
| 无自动解决合并冲突 | 产品文档明确列为「暂不实现」 |
| 无 AI 自动拆分需求 | 本批只做手动创建任务 |
| 无多厂商切换 | 执行层只接 Codex |
| 时间线不做 Markdown 富文本渲染 | 首版不引入解析器；当前保留段落、换行，把代码样式行识别为等宽块。**如果后端消息大量使用 Markdown，需要补渲染器** |
| 无虚拟滚动 | 演示数据量小。真实长会话（数万事件）必须加，否则会卡 |
| 无持久化 | 刷新页面回到种子态。真实接入后状态由服务端持有 |
| 界面里没有 Token 用量展示 | 见接口需求 §9.6：口径待定，且**不应展示"节省了多少"这类未经证实的指标** |

### 演示模式特有的行为（接入真实执行后应移除）

1. 顶部"演示模式"说明条（`.demo-strip`）
2. 集成对话框里的「演示：选择集成的结果」三选一——真实集成结果由 Git 与检查决定
3. 运行中任务的自动推进脚本（`mock/script142.ts` + `state/context.tsx` 的定时器）
4. 新建任务后的通用脚本（三条消息后自动判定为成功）
5. 「演示操作记录」面板
6. 顶栏的 `DemoMark` 与各处的「演示」芯片

移除方式见 [README 的迁移说明](../README.md#迁移到主项目)。

## 3. 需要技术确认的事项

按优先级排序。前三条会**直接影响界面结构**，其余是补细节。

| # | 事项 | 影响 | 需要谁确认 |
|---|---|---|---|
| 1 | 中止 / 恢复 / 补充指令的真实可用性与语义 | 决定三个关键按钮是保留、改造还是标记"暂不支持" | Codex 批次实测 |
| 2 | 审批请求能否到达前端，四种决策能否全部表达 | 决定审批卡片是否可用 | Codex 批次实测 |
| 3 | 数据是推送还是轮询；断线后如何同步 | 决定前端是维护本地事件流还是每次全量拉取 | GPT / Codex |
| 4 | `ref`（`T-142`）由谁生成 | 左栏与任务头的编号展示 | 后端 |
| 5 | 结构化 diff 由谁生成 | diff 视图的输入格式 | 后端 |
| 6 | 检查项的来源（谁定义"该跑哪些检查"） | 检查视图的完整性；当前是假数据里写死的 | 产品 + 后端 |
| 7 | 集成目标分支的规则（是否固定 main） | 集成对话框的文案 | 产品 |
| 8 | 事件时间线的分页游标 | 长会话 | 后端 |
| 9 | `acceptWithExecpolicyAmendment` 是否暴露 | 会写持久策略，风险更高 | 产品 |
| 10 | 并行任务的上限 | 右栏同时显示几条运行中 | 后端 |

## 4. 本批**没有**验证的事情（明确声明）

防止把设计当成结论：

- ❌ 没有调用过一次真实模型执行
- ❌ 没有验证过真实的文件修改、diff 生成、检查执行
- ❌ 没有验证过中止、恢复、并行、Linux 运行
- ❌ 没有验证过真实审批流程
- ❌ 没有性能测试（大量任务、长事件流、上千文件 diff）
- ❌ 没有真实用户可用性测试

原型能证明的：**交互路径设计自洽，状态语义在界面上不可混淆**。
原型不能证明的：**这套设计在真实执行下是否够用**。

## 5. 如果只能改三处

给下一批的建议优先级：

1. **补虚拟滚动与事件分页**。长会话是唯一会让界面真正卡死的场景，而它一定会出现。
2. **把 `Assumption` 徽标换成 Codex 实测结论**。界面上挂着 8 个"设计假设"不可长期存在——要么验证后转正，要么降级。
3. **给「检查」视图加"这次改动影响了哪些检查"的映射**。当前所有检查都平铺展示，用户不知道哪几项与本次改动相关。这需要后端提供文件到检查的映射关系，属于跨模块需求，需要先与 Codex 协调。
