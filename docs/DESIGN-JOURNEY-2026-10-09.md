## 19 个关键场景

1. 安装完成：打开工作站。
2. 首次打开：解释用途，允许稍后配置。
3. Agent 配置：工具检测、实例命名、模型与细分能力；不凭配置声明账号可用。
4. 项目首页：首次真实空态，示例项目另行标识。
5. 从零创建：名称、目标、新目录与明确新建仓库同意。
6. 接入已有项目：只读检查、未提交保护、固定 commit 与现状说明。
7. 新项目工作区：手动任务或负责人草案入口。
8. 角色、成员与负责人：项目分工、可复用职责、同工具多个实例。
9. 添加任务：目标、执行者、完成条件；分组与依赖按需展开。
10. 审阅批准：具体工作集合、依赖、基线、执行影响；批准和开始分别存证。
11. 项目流程：层级分组、依赖线、工具/实例/状态/原因，不编造进度百分比。
12. 任务会话：单任务、模型证据、成果入口、可收起工作依据。
13. 双会话：主动选择第二任务，独立草稿和订阅，不代表执行并行。
14. 成果审查：diff、真实检查命令和对象、完成条件、提出修改或确认。
15. 显式交接：来源版本、接收任务、可编辑内容与发送事实。
16. 集成与联合检查：具体成果、专用分支、冲突与失败出口。
17. 最终验收：绑定具体集成版本和检查，保留未完成问题，不自动部署。
18. 异常：断线、配置漂移、未知运行与未知写入结果。
19. 生命周期：后台继续/停止后退出、通知、重开、归档与备份边界。

## 必须在实现前解决的契约问题

- 创建组织项目不等于创建仓库。本稿的新仓库、原生目录选择与受信执行授权仍需设计并实现；不能让 HTTP 任意路径自授权。全新 Git 仓库需要可追溯的初始基线，初始提交内容、时机与同意范围待定；示例画面不代表无 commit 已可执行。
- “批准并开始”是用户操作编排建议，底层仍须逐步执行保存/批准/任务创建/准备/启动并显示失败停在哪一步；响应未知保留原请求，不用一个假原子按钮掩盖多步结果。
- B07 当前每次草案编辑使全部旧批准失效，新修订建新任务。本稿明确提示该现状；更精确的影响范围与显示名修改豁免待评审，不能只在前端放松。
- “确认成果并完成任务”是减少重复确认的交互建议，可分别保存 Acceptance 与节点人工确认。当前接口顺序和失败处理需适配；检查通过不能自动代替用户确认，也不自动集成。
- AI 规划、DeepSeek、交接、并行、归档、集成、桌面通知、安装与恢复属于后续目标，不能用此稿冒充现有能力。
- 图中“执行中”只表示运行事实；阶段说明须有事件证据。模型未报告显示未知；配置模型和路由报告不能冒充物理模型。

## 前端交付方式

先让用户评审页面用途、布局、文案和操作顺序。通过后按场景交付，而非照搬 19 页一次实施。第一条主线为安装后进入→配置一个 Agent→从零建立项目→安排首个任务→明确批准与执行→审阅成果。后端只补这条主线的必要缺口。多 Agent 流程为项目核心，简化首次入口不删角色与层级。

本轮轻量验证仅脚本语法、19 场景可渲染、少量关键截图和页面错误；不跑产品测试、真实模型或新增测试框架。
