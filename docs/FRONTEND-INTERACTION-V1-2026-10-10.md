对，这才是我们现在最应该研究的部分。

先不讨论增加什么功能，也不急着设计好看的 UI，而是先设计你实际使用 AgentDesk 时的每一次操作。

例如：

- 打开软件，第一眼看到什么？
- 我想新建项目，应该点哪里？
- 我想让 Codex 帮我规划，怎么打开策划对话框？
- Codex 提出了五个任务，我如何将它们变成流程图？
- 我想把其中一个任务交给 Claude Code，应该怎么点？
- Agent 回复了，我在哪里看到？怎么回复？
- 我不满意结果，怎么让它继续修改？
- 我确认这个任务完成了，后面的任务又怎么开始？

我们应该先把这些流程设计通顺，再让 Codex 按照交互方案改造前端。

# AgentDesk 前端交互设计 V1

## 一、先确定整体交互规则

我建议 AgentDesk 采用一种比较统一的桌面操作方式。

| 操作类型               | 使用什么交互       |
| ------------------ | ------------ |
| 切换项目、进入主要功能        | 页面切换         |
| 查看任务、修改任务、选择 Agent | 右侧面板         |
| 与策划 Agent 商量       | 可调整宽度的右侧对话面板 |
| 查看任务完整会话与代码改动      | 进入任务工作台      |
| 下发任务、批准计划、确认高风险操作  | 确认弹窗         |
| 新增任务、编辑任务名称        | 轻量面板或就地编辑    |
| 任务状态变化、执行异常        | 节点状态 + 待办通知  |

尽量避免弹窗套弹窗，也不要每点一个按钮就跳转到新页面。

普通操作优先在当前界面完成。只有进入需要长时间工作的区域，例如任务会话，才切换主要工作区。

## 二、整个软件的页面结构

1\. 项目首页

创建、导入、选择项目，查看需要处理的事项

2\. 项目工作区（核心）

项目蓝图

任务、依赖、状态

右侧面板

策划对话 / 任务详情

3\. 任务工作台

会话、执行反馈、文件改动、成果确认

软件实际上只需要这三个主要层级，再加一个设置入口和全局待办入口。

下面就以开发一个名叫 LogLens 的桌面日志分析工具为例，完整走一遍。

这是你明确希望保留的一个重点功能。

假设你刚创建 LogLens，流程图还是空的。

### 第一步：点击「与 AI 策划」

右侧展开一个独立的对话面板。如果该项目尚未配置策划 Agent，第一次打开时显示：

选择一个 Agent，长期与你讨论这个项目的开发计划。也可以稍后设置。

讨论策划助手初始化流程本卡片仅用于交互方案讨论，不连接实际 Agent。

这一步配置一次即可。之后你每次进入 LogLens，都可以重新打开同一个策划会话。

策划助手也不一定只能负责规划。你可以向它询问整个项目的进展，但它只能基于 AgentDesk 实际提供的任务及执行信息回答。

## 六、场景四：我想自己增加或修改任务

右侧出现一个简单面板：

这里不应该出现“创建角色”“绑定成员”“节点修订”等内部术语。

同一个 Codex 可以有“Codex · 规划”和“Codex · 后端”两个配置，用户直接选具体实例即可。

### 其他操作

| 操作            | 预期交互                 |
| ------------- | -------------------- |
| 点击已有节点        | 右侧查看任务详情             |
| 点击「编辑」        | 在右侧原位置进入编辑状态         |
| 点击节点上的 `+`    | 创建与当前节点关联的后续任务       |
| 从一个任务拖线到另一个任务 | 预览依赖关系，确认后进入计划草稿     |

编辑普通任务不需要全屏弹窗。

不过对已经执行中的任务，不能随便修改它的目标、工作区和依赖并立即覆盖当前执行。应创建调整草稿或要求用户先处理当前任务。

## 七、场景五：把任务真正下发给 Agent

这一步是 AgentDesk 区别于普通流程图软件的关键。

### 第一步：点击任务节点

例如点击“日志解析器”。

右侧出现任务详情：

T02 · 核心功能

## 日志解析器

尚未开始

任务说明

实现本地日志文件读取、解析与过滤。

执行者

Codex · 后端

更换

前置任务

T01 数据格式设计 · 已确认

下发任务&#x20;

### 第二步：点击「下发任务」

这时才弹出正式的执行确认窗口。

窗口告诉你这次到底会启动什么：

- 执行者：Codex · 后端
- 要执行的任务：日志解析器
- 工作区：为 T02 创建的独立 Git worktree
- 代码基线：当前已经确认的提交
- 任务上下文：任务要求及相关的已确认约定

并提供“取消”和“确认下发”。

确认后才调用已有后端启动执行。

如果当前另一个任务正在运行，而后端仍是全局串行，那么按钮应该显示 「加入执行队列」，任务状态明确变为“排队中”，而不是虚假显示为“执行中”。

如果选的是尚未支持的 DeepSeek Harness，则直接解释不可执行的原因，不应该等点击后才报出含糊的接口错误。

对于已有外部终端会话，可另设「关联外部会话」路径；在可靠双向连接能力尚未实现时，仅提供记录或复制任务指令等实际支持的操作，不能假装已经将消息送达。

### 第三步：下发之后发生什么？

成功接收执行请求后：

1. 流程图节点更新为“排队中”或“执行中”。
2. 系统自动建立或关联任务执行会话。
3. 右侧面板显示“查看执行”。
4. 你可以留在流程图继续安排其他任务，也可以进入会话工作台。

这里我建议不要强制自动跳转到会话页面。

你可能一次想下发多个任务，不应该每下发一次就被带离流程图。

## 八、场景六：Agent 执行过程中，我怎么查看反馈并回复？

假设任务已经下发给 Codex。

### 第一步：在流程图中双击“日志解析器”

进入任务工作台。

我建议采用下面这种布局：

### T02 · 日志解析器

LogLens / 项目蓝图 / 任务会话

会话记录自动保存

文件改动 · 检查结果 · 执行日志

任务会话示意。运行中是否支持立即插入消息，应由当前 Agent 适配器的真实能力决定。

### 第二步：我想让 Codex 修改某个地方

例如你看到测试失败，输入：

“把异常日志格式处理好，另外不要改动现有接口定义。”

点击发送后，要区分两种情况。

| 当前状态                 | 发送后的行为                        |
| -------------------- | ----------------------------- |
| Agent 已结束本轮执行        | 调用精确续接能力，把反馈交给原任务会话           |
| Agent 正在运行，且支持实时输入   | 将消息发送到当前运行会话                  |
| Agent 正在运行，但暂不支持实时输入 | 明确提示不能即时送达，可保存为待发送反馈或等本轮结束后续接 |
| 会话状态未知               | 禁止假装发送成功，要求先检查状态              |

从用户体验上，我仍然希望这些都通过同一个会话输入框完成。

但是界面上的发送按钮及提示文字要根据能力变化，不能统一假设所有工具都支持实时双向通信。

### 第三步：Agent 主动向我提问

例如 Codex 反馈：

> 日志格式存在两种时间表示方式，是否需要同时兼容？

AgentDesk 应该把这种需要人工回复的问题凸显出来，而不是埋在普通日志里。

此时：

- 会话页面显示问题卡片。
- 项目流程图上的 T02 变成“等待回复”。
- 右上角“待我处理”增加一条事项。
- 你点击该通知，直接进入 T02 对应的问题位置。

你可以在原会话中回复：“两种都支持，优先兼容 ISO 8601。”

如果该执行器支持对应的反馈续接，就继续原任务，而不是新建一份任务。

对于尚未真实验证的审批、恢复等能力，界面需要明确标出支持边界。

假设 Codex 完成了 T02。

它报告：

这时不能直接把节点改成已完成。

我建议显示“待审查”。

### 第二步：我不满意结果

点击「要求修改」，自动打开会话输入区，可以写：

“异常处理不够完善，增加空文件和乱码数据的测试。”

发送后，AgentDesk 通过当前支持的续接方式让原 Agent 继续修改。

旧成果和检查记录保留，新的执行结果形成后续版本。

### 第三步：我满意结果

点击「确认成果」。

弹出简短确认窗口，说明这次确认的是哪个任务、哪个代码版本。

确认后，T02 的状态变为“成果已确认”。

这还不等于已经把 T02 的代码合并到整个项目。

接下来可以出现两个明确的动作：

- 交接成果：选择一个 Agent，把当前成果摘要、相关文件和代码版本信息交给它。
- 返回项目蓝图：检查后续任务是否已经具备执行条件。

由于当前正式的跨 Agent 显式交接和集成功能尚未完成，前端第一阶段可以先保留入口和设计，不能把未实现的操作装作可用。

## 十、场景八：一个任务完成，怎样继续下一个任务？

这正是流程图应该发挥作用的地方。

例如：

```
T01 需求规划          ✓ 已确认
        │
        ├───────────────┐
        ↓               ↓
T02 日志解析        T03 界面开发
  ✓ 已确认            ✓ 已确认
        │               │
        └───────┬───────┘
                ↓
         T04 联合测试
          ● 可以下发
```

假设 T02、T03 的前置成果已经符合相关条件，T04 可以进入待下发状态。

你点击 T04：

1. 右侧展示任务要求和执行者。
2. 显示 T02、T03 的已确认成果与可交接版本。
3. 如果 T04 尚未分配 Agent，可以在右侧选择 Codex · 测试。
4. 如果缺少需要显式交接的资料，先提示处理交接。
5. 所需条件满足后，点击「下发任务」。
6. 确认执行内容并启动。

这里不需要自动调度整个项目。

由你决定什么时候开始下一个任务，AgentDesk 负责提示条件是否满足，并整理好执行所需的信息。

## 十一、场景九：第二天打开软件，如何继续昨天的项目？

这个场景也很重要，因为个人项目往往会连续开发很多天。

我建议不要弹出一大堆“上次会话恢复向导”。

你进入 LogLens 后，直接看到上次查看的流程图位置，右上角显示“待我处理”。

例如：

## 待我处理

T03 · 界面开发

Claude Code 等待你回复一个接口问题

T02 · 日志解析器

Codex 已提交成果，等待审查

T05 · 测试任务

执行状态未知，需要重新核查

点击任何一项，直接打开对应的任务和具体问题，而不是只跳转到项目首页。

## 十二、最后把前端主要动作统一起来

这是我建议交给前端开发时作为约束的一张表。

| 入口或按钮   | 点击后              | 是否需要二次确认     |
| ------- | ---------------- | ------------ |
| 新建项目    | 打开创建项目窗口         | 创建前确认信息      |
| 项目卡片    | 进入项目蓝图           | 否            |
| 与 AI 策划 | 展开项目级策划会话        | 否            |
| 生成计划草稿  | 中央显示候选流程         | 否            |
| 批准计划    | 校验并发布新计划版本       | 是            |
| + 新建任务  | 打开右侧任务编辑面板       | 加入草稿不需执行确认   |
| 单击任务节点  | 打开右侧任务详情         | 否            |
| 双击任务节点  | 进入任务工作台          | 否            |
| 更换执行者   | 打开 Agent 选择列表    | 影响运行任务时需要确认  |
| 下发任务    | 显示执行内容与工作区       | 是            |
| 查看执行    | 打开任务会话           | 否            |
| 发送反馈    | 按执行状态发送或续接       | 普通反馈通常不需额外确认 |
| 要求修改    | 进入反馈输入状态         | 实际续接时按能力执行   |
| 确认成果    | 展示要接受的成果版本       | 是            |
| 交接成果    | 选择接收 Agent 与交接内容 | 是            |
| 返回蓝图    | 返回上次的流程图位置       | 否            |

### 我还建议明确三个前端状态原则

第一，不能每个按钮都在任何时候可点击。 例如一个任务依赖未满足，就应该显示为什么暂不能下发；如果 Claude Code 的某种恢复操作尚未真实验证，就应该准确展示限制。

第二，尽量不要丢失用户当前的位置。 从流程图进入会话，再返回时，应恢复此前的缩放比例、画布位置和选中的任务；策划对话收起再展开也应保留原会话。

第三，一个操作只有一个主要入口。 例如下发任务主要从任务详情执行，不要在项目列表、流程图、会话页、Agent 配置页各做一套不同的下发逻辑。

## 十三、接下来我建议如何开展前端重构

不是立刻让 Codex 开始重画全部页面，而是分两步。

第一步：先审查现有前端。

让 Codex 根据实际代码，整理当前所有页面、路由、按钮、对话框与后台接口的对应关系。尤其要检查哪些操作已经可以完成，哪些只是页面入口，哪些依赖尚未实现的后端能力。

第二步：按真实用户路径逐条重构。

我建议先打通最重要的完整路径：

进入项目

与策划 Agent 讨论并批准计划

在流程图上选择任务

选择 Agent 并下发任务

查看反馈、发送修改要求

审查并确认成果

这条链路走通了，再优化并排会话、工作区详情、交接、成果集成等操作。

我认为这份设计可以作为 AgentDesk 前端交互规范的第一版，而不是直接作为开发完成标准。 因为现在还没有对照你真实的前端代码，无法判断具体哪些页面应当复用、重排或删除。

接下来最有价值的事情，是让 Codex 先针对现有前端做一张 “当前操作路径 vs 目标操作路径” 的对照表。之后我们就可以从第一步“进入项目”开始，一屏一屏确定：页面怎么布局、按钮放在哪里、点击后怎么变化、哪些现有组件可以复用。

这样重构出来的就不是凭想象做的新 UI，而是真正符合你日常使用习惯的 AgentDesk。
