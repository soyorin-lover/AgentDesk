# AgentDesk：应用视觉与交互重设计提示词

请作为 AgentDesk 的前端与体验设计负责人，重新设计这个产品。先交付可供评审的视觉与交互方案，再进入完整实现。

本提示词取代旧批次提示词中与本次审美、产品定位和布局要求冲突的内容。最新用户指令优先。

## 一、先理解产品

AgentDesk 是独立开发者长期使用的个人开发工作台。用户围绕软件项目组织任务，选择 Coding Agent 执行，跟进工作、处理问题和审批、审查代码与检查结果，最终完成集成和验收。

长期至少管理 Codex、Claude Code、DeepSeek Harness，未来可能加入更多引擎。请围绕通用的项目与任务设计，不要把产品写成 Codex 专用工具。当前只有 Codex 已完成最小真实接入验证；其他引擎的接入与能力不能在原型中冒充已经实现。

产品以单用户、本机 Web 应用起步，目标 Windows 和 Linux，主要通过桌面键盘和鼠标使用。它需要具备持续使用的应用体验：导航稳定、操作连贯、工作状态可保留、空间可调整。

Claude 负责前端设计与实现；Codex 负责接入、后端、Git 工作区和集成；DeepSeek 负责简单辅助工作。本轮重点是前端视觉与体验，不扩展后端或自动编排。

## 二、用户真正想要的视觉感受

浅色、安静、精致、现代简洁，适合长时间使用，看着舒服。精致感应来自排版、比例、间距、对齐、轻微层次与细腻反馈。

用户提供的参考是 Codex、Claude、DeepSeek Harness 的桌面端截图，以及一张浅色网站截图。参考价值在于它们的设计思维：界面克制、内容突出、功能按需出现、辅助空间可以开合。

请认真分析提供的截图，解释你提炼出的共同语言，并转化为适合 AgentDesk 的设计。不要照搬某一家的界面，不要拼接几家的侧栏、输入框与配色，也不要因为参考里有三栏就固定做三栏。

如果没有收到这些截图，明确说明你的参考依据来自本提示词的文字描述，不要声称看过图片。无需因此暂停设计。

可作为探索起点的方向：

- 接近白色的主工作面，浅灰或轻微冷色的应用外框与导航区域。
- 深灰正文、清楚的辅助文字，少量强调色用于交互与选中。
- 自然排布的正文与列表，通过留白、排版和轻分隔建立秩序。
- 柔和的选中态、统一的图标、克制的圆角；浮层和输入区可有细微阴影。
- 舒适的文字尺寸和行距，长段内容控制阅读宽度。

具体颜色、尺寸和比例由你通过画面推敲；这些起点不是让你机械套用的模板。

避免：大面积警报色、密集状态徽章、层层卡片包裹、厚重边框、装饰性渐变、过多阴影、为了显得专业而缩小文字，以及为了简洁把文字做得难以辨认。不要为了填满空间添加没有用途的统计卡片或图表。

## 三、模块化与渐进展开

初始界面不能一次展示整个系统的信息。项目、任务、执行、审查、交付、智能体管理应有清楚的关系，并通过合适的导航逐层进入。

请自己判断模块如何组织，哪些应为独立页面，哪些适合局部视图、标签或辅助面板。不要机械地把每项功能都变成一个一级菜单。

每个界面要能回答：用户现在在做什么、最应该看到什么、下一步可以做什么。默认呈现当前所需的信息，目标详情、历史记录、完整工具输出和技术诊断按需查看。失败与审批影响等决策必要信息不能隐藏。

同一页面避免在任务列表、标题区、右侧面板中反复展示相同状态和说明。跨任务待处理事项需要易于发现，但其呈现方式由你设计，不要求常驻右栏。

## 四、可开合、自适应的工作空间

这是明确要求：各类辅助栏可以按需打开和关闭，空间随之重新分配。可能包括导航、任务列表、文件浏览、文档预览、变更审查等；具体哪些采用栏式呈现由实际用途决定。

- 关闭后释放占用空间，保留清楚的重新打开入口。
- 打开后主区自然重排，文字、输入区与工具栏适应可用宽度。
- 适合并排工作的区域支持拖动分隔线调整宽度，记住用户偏好。
- 设置合理的最小宽度；窗口不足时收起、切换或重排辅助内容，避免把所有区域一起压缩。
- 主区变宽时仍保持舒适阅读宽度；代码审查可以使用更宽空间。
- 开合与调整不丢失输入草稿、打开内容和阅读位置。
- 让用户能专注当前工作，也能在需要时并排查看相关材料。

请根据 AgentDesk 的工作流决定布局。默认打开几栏、哪边放什么，不由参考截图直接决定。也不要求首轮实现任意拖拽停靠、复杂多窗口或完整 IDE。

## 五、核心场景与业务边界

核心流程：打开项目 → 创建任务与验收条件 → 选择可用智能体 → 执行 → 处理问题/审批 → 查看 diff 与检查 → 要求修改或接受 → 集成 → 最终验收。

设计需要容纳：没有任务、正在执行、等待用户、待审查、执行失败，以及多个智能体分别负责不同任务。多智能体管理不等于已经确定自动调度或同任务自动协作。

保持业务含义准确：

- 执行完成、用户接受、代码集成与最终验收是不同阶段。
- 关闭页面不取消运行；中止不回滚已有变更。
- 会话恢复不代表恢复已结束的系统进程。
- 各引擎能力分别验证，不默认拥有相同审批、恢复和补充指令能力。
- 原型和模拟执行明确标识，可用简短常驻提示，避免占满工作空间。
- 检查未运行时明确写未运行，不能画成通过。

## 六、本轮如何交付

先简短说明你的设计判断：视觉语言、信息层级、模块关系与布局如何服务使用场景。然后提交可以直接看到的高保真画面或轻量可交互视觉样稿，不要只交文字说明或抽象线框。

优先做同一套设计下的关键状态：

1. 进入项目：内容不多时自然、有秩序，能找到继续工作的入口。
2. 任务执行：真实长度的中文交流、工具活动与输入区，辅助栏关闭时能专注工作。
3. 同一任务打开辅助面板：展示文件、文档或变更，说明开合前后空间如何重排，并展示调整宽度后的效果。
4. 代码审查：diff 有充分空间，检查证据与修改/接受操作清楚。
5. 智能体管理：清楚区分不同引擎、配置实例、连接状态和未接入状态。

补充一张较小窗口的关键布局，验证空间不足时的取舍。设计基准可采用 1440 × 900，同时检查 1280 × 800；这是建议基准，不要求固定像素画布。

请使用有代表性的内容验证设计：长任务名、多条消息、多个文件、失败说明。不要依赖大量空白或短占位文字掩盖内容增长后的布局问题。

交付应说明字体、颜色、间距、圆角、图标和状态规范，包含键盘焦点、选中、悬停与错误状态。当前优先做好浅色主题，不扩展暗色或移动端整套设计。

本轮先评审视觉与布局，再铺开完整可点击流程和产品代码。可以复用现有原型中可靠的状态与交互逻辑；视觉和信息结构需要重新判断，不局限于换皮。
